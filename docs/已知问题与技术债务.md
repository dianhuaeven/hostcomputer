## 一、🔴 复现性 Bug：operator_input 被静默丢弃（emergency_active 卡死）

### 现象
某些情况下，来自上位机的控制信号（车体 / 机械臂运动）被下位机**静默丢弃**，车不动。
- **重启下位机节点可临时修复**，重连上位机无效。
- 曾怀疑 TTL 时间门限（两端时钟不对齐），删除 TTL 后问题依旧。

### 根因
下位机 `bridge_core.py` 处理 operator_input 时有三条丢弃路径：

| 路径 | 条件 | 位置 | 现状 |
|---|---|---|---|
| `dropped_expired` | TTL 过期 | `bridge_core.py:663` | 已实质禁用（`ttl_ms` 默认 0） |
| `dropped_old_seq` | `seq <= 水位` | `bridge_core.py:661` | 生效，但 client 重连会清水位 |
| **`ignored_emergency`** | **`emergency_active == True`** | **`bridge_core.py:666`** | **真凶：无任何自愈机制** |

一旦 `emergency_active` 被置 True，之后**所有** operator_input 走 `ignored_emergency` 分支——被忽略 + `publish_zero`（停车）+ 水位照涨，直到急停被显式清除。

### 决定性证据（为什么是"重启下位机"而非"重连上位机"）
client 连接时调用的 `reset_operator_input_session`（`bridge_core.py:378`）清了 `last_operator_seq` / `watchdog_active` / `last_pressed_keys` / `last_valid_input_ms`，**唯独没清 `emergency_active`**。而 `emergency_active` 是 `BridgeCore` 单例的全局状态（`bridge_state.py:73`），只能靠 `clear_emergency` 命令或 `system_command(command=clear_emergency)` 清除（`bridge_core.py:529`、`:540`）。

这恰好解释了全部现象：
- **信号被静默丢弃** → operator_input 全走 `ignored_emergency`（只有下位机 events 日志有一行 warning，上位机无感）
- **删 TTL 没用** → 根本不是 TTL 那条路径
- **重启下位机可临时修复** → 进程重启，`BridgeState` 重新初始化，`emergency_active` 回到默认 `False`
- **重连上位机无效** → reset 漏清了 `emergency_active`，只有进程重启才恢复

### 触发链（推断）
急停被置位（Space / 手柄 L3+R3 / 急停按钮）后，清除命令 `clear_emergency` 没有成功落地（ACK 丢失，或上位机清除路径本身脆弱——见系统性问题 #4）。之后 `emergency_active` 永久 True。

### 确诊方法（下次复现时查下位机 events 日志）
- 出现大量 `operator input ignored emergency` 且无对应 `emergency cleared` → **实锤本 bug**
- 出现 `operator input dropped old seq` → 是 seq 水位问题
- 出现 `operator input dropped expired` → TTL 残留

### 修复方案（待硬件可用后实施）
| 方案 | 做法 | 风险 |
|---|---|---|
| **A** | 上位机连接 / 重连后主动发 `clear_emergency`，或 `sync_request` 同步急停态后再决定 | 最保守，治标，**上位机可独立实施** |
| B | `reset_operator_input_session` 里也清 `emergency_active` | ⚠️ 网络抖动重连会擅自解除急停，有安全责任风险 |
| C | 修上位机急停清除路径为可靠单入口 + ACK 必达重发 | 治本，改动大 |

**推荐 A + C 组合**。B 不建议单独使用（急停自动解除是安全红线）。

### 次要：`nextSequence()` 非线程安全
`ROS1TcpClient.cpp:573` 的 `++m_nextSequence` 无锁，心跳 / UI / 手柄多线程调用会导致 seq 重复或乱序，边缘情况下触发 `dropped_old_seq`。修法：`QAtomicInteger` 或 `QMutex`。

## 二、系统性设计问题（跨模块根因）

### #1 Controller 退化为透传层，业务逻辑漏到 UI 层
- `controller.h/.cpp` 只持有 `ROS1TcpClient*`，11 个 `sendXxx` 全是"判连接 → 转发"两行壳；不持有 `KeyboardController` / `HandleKey`，无模式状态机。
- 后果：
  - ① 键盘(10Hz) + 手柄(50Hz) **双输入流未合并**成统一 operator_input 快照；
  - ② Vehicle/Arm **模式切换不清理残留按键**（切模式瞬间残留速度指令，高危）；
  - ③ `MainWindow` 被迫膨胀为约 1793 行上帝对象。
- 位置：`src/controller/controller.cpp` 全文

### #2 IMU / 关节数据高频直冲 3D 渲染，无节流无校验
- `mainwindow.cpp:710` 直接 `updateAttitude()` → `RobotViewModel.cpp:5` 用 `!=` 比较浮点 → 每帧 `emit *Changed()` → QML 3D 重绘。50–100Hz 远超 60Hz 显示，纯烧 GPU。
- 且无 `qIsFinite` 校验；下位机送 NaN 时 `NaN != NaN` 永真，触发持续信号风暴，QtQuick3D 对 NaN 行为未定义。
- 位置：`src/controller/RobotViewModel.cpp:5-27`、`mainwindow.cpp:710-730`

### #3 视频栈同步 stop + 跨线程信号竞态
- `FfmpegRtspDecoder.cpp:86` 的 `stop()` 是 `wait(2000)` 同步等线程退出；5 路关窗串行 → 主线程最坏冻结约 10s，Windows 弹"无响应"。
- decoder 在 worker 线程 `emit failed/started` 走 `QueuedConnection`，`stop()` 期间排队事件可能投递到正在销毁的对象 → use-after-free；worker 未干净退出即 `delete` → Qt `qFatal`。
- 位置：`src/controller/FfmpegRtspDecoder.cpp:81-98`、`RtspPlayerWidget.cpp:124-129`

### #4 急停多入口、真相源缺失
- Space 键至少 3 条路径（`QShortcut` + `keyPressEvent` + `keyReleaseEvent` 吞键 + `KeyboardController` 信号），靠 150ms 去抖掩盖重复。
- 本地无"当前是否急停"的权威标志，靠按钮闪烁 / 日志判断。**清除路径（`clear_emergency`）脆弱——这正是本文件第一章 bug 的上位机侧诱因。**
- 位置：`mainwindow.cpp:137`、`:776`、`:790`、`:534`

## 四、死代码 / 孤儿文件

- **`calculator.html`**（根目录）：无关的网页计算器，不在 CMake / qrc，应删除。
- **`CO2DisplayWidget`**：整个控件无人调用，CO2 实际显示在 `TelemetryPanelWidget`；两套阈值(800/1500) + 两套色值体系并存。
- **`m_textData` + `updateJointsData`**（`mainwindow.cpp:721`）：35 行死代码每帧白跑。
- **`action_about`**：UI 文件定义了但未 `addaction`，"关于"菜单永不显示。
- **`ErrorHandler`**：声称被各层依赖，实际仅通信层引用。
- **状态显示职责重叠**：`TelemetryPanelWidget`(8 格) 与 `ControlPanelWidget` / `CO2DisplayWidget` / `GamepadDisplayWidget` 大量重复显示同一份数据，阈值 / 色值 / 文案各维护一套。

## 五、建议修复优先级

1. **止血（上位机可独立验证，约 1 周）**
   - 视频栈 `stop()` 改异步 + 修跨线程信号竞态（防崩溃 / 防卡死，用户立刻感知）
   - `nextSequence()` 加锁
   - 清理死代码（`calculator.html` / `CO2DisplayWidget` / `m_textData`）
2. **emergency 卡死应急（上位机侧，方案 A）**
   - 上位机重连后主动同步 / 清除急停态，降低复现概率。彻底修复待硬件。
3. **还魂（约 2–3 周）**
   - Controller 重构：收编 `KeyboardController` + `HandleKey` 为单一输入快照 + 模式状态机（一举解决系统性问题 #1/#2/#4）
4. **刮骨（持续）**
   - 协议解析下沉到专门 Handler；UI 状态显示控件去重；修日志轮转 / Meyers 单例问题
